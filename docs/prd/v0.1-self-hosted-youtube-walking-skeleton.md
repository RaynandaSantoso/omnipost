# PRD: OmniPost v0.1 — Self-hosted YouTube upload walking skeleton

Status: ready-for-agent

> Supersedes `v0.1-youtube-shorts-walking-skeleton.md`, which assumed a localhost-only app running against the author's own platform credentials. That model was abandoned after the hosting, OAuth-verification, quota, and account-safety constraints were investigated. See *Further Notes*.

## Problem Statement

As a solo content creator, I make one vertical short and then manually upload it to YouTube Shorts, TikTok, and Instagram Reels — repeating the same tedious steps (open each app, pick the file, re-type the caption, wait, confirm) three times per video. It's slow, repetitive, and easy to get wrong.

Existing hosted tools that solve this want a subscription and, more importantly, want custody of my platform credentials — an account-takeover risk I don't accept for accounts that *are* my livelihood. I want to press one button and have my short published everywhere, without handing my publishing rights to a third party.

This PRD covers **v0.1 only**: the walking skeleton proving the whole pipeline against a single platform (YouTube). TikTok and Instagram are deliberately deferred so the hardest integration risk is not front-loaded.

## Solution

**Self-hosted, single-tenant software.** You clone the repo, run one command to bring it up, register your own developer apps with each platform, and paste your own credentials into your own config. Your tokens live in your database on your infrastructure and are never transmitted anywhere except to the platform that issued them.

From the dashboard you connect your YouTube account once, select a video, type a title and description, and click Upload. The app enqueues a durable background job, returns immediately, and shows live status (pending → uploading → done/failed) ending with a link to the published video.

Self-hosting is not a compromise here — it is what makes the product viable. Because each operator is the sole user of their own platform apps, Google's OAuth verification requirement does not apply, API quota is per-instance rather than shared, and there is no multi-tenant credential store to breach.

The architecture is built from day one to extend to TikTok and Instagram (a `PlatformAdapter` boundary and a durable job model), but v0.1 only wires up YouTube.

## User Stories

**Installation and operation**

1. As an operator, I want to bring the whole application up with a single command, so that I can self-host it without assembling infrastructure myself.
2. As an operator, I want the app to run as a container with a documented volume for its data, so that my uploads and credentials survive a restart or upgrade.
3. As an operator, I want all secrets supplied through environment variables rather than committed files, so that I never risk checking my credentials into git.
4. As an operator, I want the app to validate its configuration at startup and fail immediately with a clear message naming the missing or malformed variable, so that I find out about a misconfiguration at boot rather than mid-upload.
5. As an operator, I want database migrations to run automatically on startup, so that upgrading is pulling a new image and restarting.
6. As an operator, I want a health endpoint reporting whether the app is up and its database reachable, so that my platform can restart it when it is unhealthy.
7. As an operator, I want the app to finish or safely release in-flight jobs when asked to shut down, so that a deploy doesn't corrupt or strand an upload.
8. As an operator, I want step-by-step setup documentation for obtaining each platform's credentials, so that the 30-plus minutes of console clicking is guided rather than guesswork.
9. As an operator, I want to protect my deployed instance with a single shared password, so that putting it on a public URL doesn't expose my publishing rights to the internet.
10. As an operator, I want to run the app on my own machine without a password, so that purely local use has no friction.

**Connecting a platform**

11. As a creator, I want to connect my YouTube account via Google sign-in, so that the app can upload on my behalf without me sharing a password.
12. As a creator, I want the app to remember my YouTube connection between restarts, so that I don't reconnect every session.
13. As a creator, I want to see whether my YouTube account is currently connected and which channel it is, so that I know the app is ready and pointed at the right place.
14. As a creator, I want to disconnect my YouTube account, so that I can revoke the app's access.
15. As a creator, I want my access token refreshed automatically when it expires, so that uploads keep working without me re-authenticating.
16. As a creator, I want a clear "reconnect needed" state when a refresh fails, so that I get an actionable instruction instead of a cryptic error.
17. As a creator, I want my stored tokens encrypted at rest, so that a leaked database file or backup does not hand over my channel.

**Uploading**

18. As a creator, I want to select or drag-and-drop a video file, so that I can choose the short I want to publish.
19. As a creator, I want to see the selected file's name, size, and duration before uploading, so that I can confirm I picked the right video.
20. As a creator, I want to enter a title, so that the video is labelled correctly.
21. As a creator, I want to enter a description, so that my video has context and links.
22. As a creator, I want to be told before the upload starts if my file is too large, too long, or an unsupported format, so that I don't wait out a doomed upload.
23. As a creator, I want to click a single Upload button, so that publishing starts.
24. As a creator, I want the Upload button to return control immediately, so that my browser doesn't freeze during a multi-minute upload.
25. As a creator, I want a dry-run mode that exercises the entire pipeline without publishing anything, so that I can verify a fresh install works before risking a real post.

**Observing the work**

26. As a creator, I want live status for my upload (pending, uploading, done, failed), so that I know what's happening.
27. As a creator, I want a progress indication during upload, so that I'm not staring at an ambiguous spinner.
28. As a creator, I want a success state with a clickable link to the published video, so that I can verify and share it.
29. As a creator, I want a failure state with a human-readable reason, so that I understand what went wrong.
30. As a creator, I want to retry a failed upload, so that I can recover from transient errors without redoing everything.
31. As a creator, I want transient failures retried automatically with increasing delays, so that a brief platform hiccup resolves itself without my attention.
32. As a creator, I want a job that has exhausted its retries to stop and wait for me, so that the app doesn't hammer a platform that is rejecting me for a real reason.
33. As a creator, I want a history of past uploads with outcomes and timestamps, so that I can see what I published and when.
34. As a creator, I want an upload interrupted by a restart to not show as permanently "uploading", so that stale jobs don't mislead me.

**Extensibility**

35. As a future multi-platform user, I want the upload flow structured around a generic platform concept, so that adding TikTok and Instagram reuses the same pipeline.
36. As a future multi-platform user, I want one upload to fan out to independent per-platform jobs, so that a failure on one platform doesn't block or roll back the others.
37. As a future multi-platform user, I want every domain record to carry an owner identifier, so that real multi-user support later is additive rather than a schema rewrite.

## Implementation Decisions

**Application shape**

- Single **Next.js (TypeScript)** application, full-stack, one process. No separate backend service.
- **SQLite** via **Prisma**, on a mounted volume. Chosen over Postgres specifically *because* the product is self-hosted: it keeps `docker compose up` to a single container with no database to provision. Prisma keeps a Postgres swap to a datasource change for operators who want one.
- **Single-tenant, no user accounts.** One seeded user row. Every domain table nonetheless carries a `user_id`, so multi-tenancy is later additive.
- **Access gate, not authentication.** An optional shared password from config; when set, all routes require it. When unset, the app runs open, which is correct for a machine-local install. This is deliberately not a user system.
- **Access gate hardening.** The password comparison is constant-time, not `===`, to avoid a timing side-channel. Repeated failed attempts are rate-limited / back off rather than accepted at unlimited speed. On success, a session cookie is issued — `HttpOnly`, `Secure` when served over HTTPS, `SameSite` — with a 30-day sliding lifetime (renews on activity). Session mechanism and lifetime are documented in the setup docs.
- **TLS is a documented deployment precondition, not something the app enforces by refusing to boot** — a reverse proxy in front of the app is the common self-hosted pattern, and the app can't always prove HTTPS is in effect from behind one. Where it *can* detect plaintext (e.g. no `X-Forwarded-Proto: https`), it logs a startup warning. Running any non-localhost deployment without TLS in front of it is documented as unsupported.

**Data model (conceptual)**

- `User` — a single seeded row.
- `PlatformConnection` — an OAuth connection for a `(user, platform)` pair: encrypted access token, encrypted refresh token, expiry, connected account identifier. v0.1 only ever holds a `youtube` row.
- `Upload` — one user-initiated publish action: source video reference, the shared title/description, timestamps.
- `Job` — one unit of background work = one upload to one platform. Holds `status`, error message, attempt count, next-attempt time, lease owner and lease expiry, and on success the resulting platform video URL. An `Upload` fans out to one `Job` per target platform (v0.1: exactly one).

**Platform adapter boundary**

- A **`PlatformAdapter` interface** abstracts "upload this video with this metadata using these credentials, report progress, and return a result or a typed failure." Failures are classified as **retryable** (rate limit, 5xx, network) or **terminal** (bad credentials, rejected content, quota exhausted) — the job engine's retry decision depends on this classification, so it belongs in the adapter contract.
- Two implementations ship in v0.1: **YouTube** and **DryRun**. The second is not a test double — it is the user-facing dry-run feature from story 25, and it exists partly so the abstraction is validated by more than one implementation before TikTok is built against it.

**Job engine**

- Jobs are **durable rows in SQLite**, which is the source of truth for status. No external queue.
- A background runner in the same Node process claims jobs by **taking a time-bounded lease**, and heartbeats while working. A job whose lease expires is reclaimable — this is what makes crash recovery work rather than a startup-only sweep.
- **On startup**, any job holding an expired lease is returned to pending. Jobs that have exhausted their attempt budget are marked failed. This satisfies story 34 and is strictly more general than "mark orphans failed."
- **Retries use exponential backoff with jitter**, capped at a configured attempt budget. Jitter is required, not decorative: unjittered backoff synchronizes retries into bursts against a platform already signalling distress.
- Terminal failures skip retry entirely and wait for an explicit user retry.
- The dashboard reads status by **polling** a status endpoint.

**YouTube integration**

- Google OAuth 2.0 authorization-code flow against **the operator's own Google Cloud project**. The operator publishes their OAuth app to **Production** status; because they are its only user, Google's verification requirement does not apply. Testing status is explicitly rejected — it caps refresh tokens at 7 days.
- **Callback validation.** The `redirect_uri` is strictly, exactly matched — not merely same-origin. A `state` parameter is generated before redirecting to Google, stored, and validated on callback to prevent CSRF against the OAuth callback.
- Upload via **YouTube Data API v3 `videos.insert`** (resumable), setting title, description, and Shorts-appropriate defaults.
- **Token refresh** is centralized: before an upload, an expired access token is refreshed and persisted.

**Encryption**

- Tokens are encrypted at rest with a key supplied via config, using an **authenticated cipher (AES-256-GCM)** — not plain AES-CBC — so a tampered ciphertext fails to decrypt rather than silently decrypting to garbage. A missing key when a connection exists is a startup failure, not a silent degradation.
- **Key rotation is explicitly out of scope for v0.1.** Changing the configured key means every existing `PlatformConnection` must be reconnected — this is documented, not silently handled. Revisit if it becomes painful in practice.
- **Log hygiene.** No access token, refresh token, or encryption key value may ever appear in application logs — including error stack traces and startup config-validation errors, which name the missing/malformed variable but never print its value. This is a testing requirement, not just a convention.
- **SQLite file permissions.** Since tokens live in the SQLite file (even encrypted), setup docs specify restrictive permissions on the database file and its Docker volume.

**API contracts (conceptual)**

- Start the YouTube OAuth connect flow; complete it via callback and persist the connection.
- Report connection status; disconnect.
- Create an upload (video file + title + description), creating `Upload` and `Job` records and returning identifiers immediately.
- Read job/upload status (polled).
- Retry a failed job.
- Health/readiness.

## Testing Decisions

**What makes a good test here:** tests exercise **external, observable behavior** — they drive the app through its real API and assert on real outcomes: job status transitions in the database, the shape of the request the app *sent* to the platform, the result surfaced to the caller. Internal function names and private helpers are never asserted directly.

**Seams — two, deliberately:**

1. **The outbound HTTP boundary to platform APIs**, faked with **MSW**. Everything inside the app runs for real: API routes, job engine, Prisma/SQLite writes, adapters. Only the network call to Google is faked. This is the highest available seam.
2. **The clock.** Lease expiry and exponential backoff are time-dependent, and testing them against real time would make the suite unusably slow. Time is injected rather than read ambiently, so tests advance it explicitly.

The second seam is a genuine addition over a naive design and should be confirmed before implementation. It is justified by the job engine's timing behavior being core product behavior rather than an implementation detail — an untested backoff curve is an outage waiting to happen.

**Modules tested:**

- **Upload pipeline end-to-end:** `POST` an upload → assert a `Job` exists as `pending` → runner processes it → with MSW succeeding, assert `done` with the video URL, and assert the request carried the correct title, description, and video bytes.
- **Retryable vs terminal classification:** MSW returns `429`/`5xx` → assert the job schedules another attempt with a longer delay; MSW returns an auth error → assert the job goes terminal without burning retries.
- **Backoff curve:** assert delays grow and carry jitter, and that the attempt budget is honoured.
- **Lease reclaim:** a job leased by a worker that stops heartbeating is reclaimed after expiry and completes exactly once.
- **Startup recovery:** seed a job with an expired lease, run startup recovery, assert it returns to pending and then completes.
- **Token refresh:** seed an expired access token, MSW serves the token endpoint, assert refresh-then-upload and that the new token is persisted encrypted.
- **Encryption at rest:** assert stored token columns do not contain plaintext, and that a tampered ciphertext fails to decrypt rather than decrypting to garbage.
- **Config validation:** assert startup fails with a message naming a missing required variable, and that the message never includes the variable's value.
- **Dry-run adapter:** assert the full pipeline reaches `done` with no outbound platform call.
- **Access gate:** with a password configured, assert unauthenticated requests are rejected; assert repeated failed attempts are rate-limited; assert password comparison is constant-time.
- **OAuth callback security:** assert a callback with a mismatched `redirect_uri` or an invalid/missing `state` is rejected.
- **Log hygiene:** drive a request that touches a token (connect, refresh, upload) and assert no log line emitted during the request contains the plaintext token or encryption key value.

**Prior art:** none — greenfield repo. This PRD establishes the MSW seam, the injected clock, and the integration-test convention that later versions follow.

## Out of Scope

- **TikTok (v0.2) and Instagram (v0.3).** Known constraints for later: TikTok's unaudited clients are limited to `SELF_ONLY` visibility with the posting account private, but **draft/inbox mode requires no audit** and is the intended v0.2 path; Instagram requires a Business/Creator account and fetches video from a public URL rather than accepting an upload, which self-hosting conveniently satisfies.
- **Real multi-user support, accounts, or roles.** Only the schema shape is in scope.
- **A hosted/SaaS offering.** The product is self-hosted by design.
- **Per-platform caption or metadata overrides.** One shared caption.
- **Scheduling** posts for a future time.
- **Video editing, transcoding, or thumbnail generation.**
- **A distributed job queue.** In-process, database-backed only.
- **Horizontal scaling.** The lease model would permit multiple workers, but a single-user instance does not need them and this is not a design goal.

## Further Notes

**Why the previous PRD was replaced.** The original design ran on localhost against the author's own credentials, with a hosted deployment considered later. Investigation killed it on several fronts at once: Google issues 7-day refresh tokens to any OAuth app in Testing status, so the app would break weekly unless verified; verification demands a domain, hosted privacy policy, and demo video; YouTube's 10,000 daily quota units against 1,600 per `videos.insert` capped the whole instance at roughly six uploads a day *shared across everyone*; and because the design had one hardcoded user with one connection, anyone given access to a deployed instance would have been operating the author's channel. Self-hosting dissolves all four — each operator is their own developer, with their own quota, their own tokens, and no one else on the instance.

**What survives that self-hosting does not fix.** Every adopter must still register their own developer apps, which is realistically 30–60 minutes of console work before the first upload, and Instagram will still require a Business or Creator account. Setup quality is therefore a product feature, not documentation garnish — it is the most likely reason someone abandons this tool.

**Portfolio framing.** The interview-worthy engineering is the durable job engine — leases, heartbeats, backoff with jitter, retryable-versus-terminal classification, crash recovery — behind a platform-adapter boundary, plus the operational surface that self-hosting demands: containerization, boot-time config validation, migrations, health checks, graceful drain. Since there is no public instance to click through, the demo surface is a recorded walkthrough and an architecture document, with the dry-run adapter making a fresh clone verifiable in one step.
